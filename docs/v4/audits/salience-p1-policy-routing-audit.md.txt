## 1. Production policy and cross-service revocation

The requirement is not “no policy code exists.” A generic `PolicyEngine` and `PolicyVersion` exist in [policy.py](/home/admin/Salience/src/salience/governance/policy.py:18). The engine accepts in-memory dictionaries of policy versions, grants, and known scopes and checks active/expired policy, allowed effect, approval, scope, and budget at [policy.py](/home/admin/Salience/src/salience/governance/policy.py:47). Its unit tests exercise those decisions in memory at [test_policy.py](/home/admin/Salience/tests/unit/test_policy.py:27) and [test_policy.py](/home/admin/Salience/tests/unit/test_policy.py:67). That is not durable production policy/revocation integration.

V4 current authority is explicitly described as local: [authority.py](/home/admin/Salience/src/salience/cycles/authority.py:1) reads the current identity and scoped grant from PostgreSQL and fingerprints that snapshot at [authority.py](/home/admin/Salience/src/salience/cycles/authority.py:10). V4 stop and permit handling serializes workspace/goal stop revisions, binds permits to fixture account/effect/purpose, rechecks current state, and permits only one claim; see [governance.py](/home/admin/Salience/src/salience/cycles/governance.py:35), [governance.py](/home/admin/Salience/src/salience/cycles/governance.py:62), and [governance.py](/home/admin/Salience/src/salience/cycles/governance.py:123). The publication authorizer checks a concrete current authorization context, but its policy input is a boolean fact and the code is not a general production policy service: [publication governance](/home/admin/Salience/src/salience/publication/governance.py:45).

Useful local coverage exists. [test_v4_cycle_governance.py](/home/admin/Salience/tests/integration/test_v4_cycle_governance.py:51) covers stop/permit ordering, expiry and retries; lines 75–100 cover a concurrent stop/claim and duplicate fixture workers; lines 243–267 cover current revocation and authority-database outage. [test_v4_legacy_publication.py](/home/admin/Salience/tests/integration/test_v4_legacy_publication.py:1006) covers revocation before fixture workflow start, line 1126 covers revocation between fixture activities, and line 2241 covers lost reconciliation scope. These are local fixture tests, not cross-service production evidence.

The matrix makes the remaining gap explicit:

- R13 says local grant/program revocation and current-authority checks pass, but “Full version revocation remains required”; remaining acceptance is “complete enabled-version revocation integration” ([matrix](/home/admin/Salience/docs/v4/p1-qualification-matrix.json:360)).
- R15 says the fixture review and publication path do not constitute a general versioned policy model or production effect gate; both remain to be qualified ([matrix](/home/admin/Salience/docs/v4/p1-qualification-matrix.json:393)).
- R18 says local fixture stop/outage and receipt-only reconciliation checks pass, while production-wide cross-service revocation, live-scheduler stop/fencing, typed recovery workers, and scoped remote reconciliation remain unqualified ([matrix](/home/admin/Salience/docs/v4/p1-qualification-matrix.json:484)).

**Conclusion:** The proposed bounded policy/revocation spec is warranted for RG1 because R13/R15/R18 identify mandatory open behavior after the local fixture slice. Keep its scope to current policy, stop/revocation, pre-dispatch reauthorization, and original-identity liability for the affected production path. Do not create another abstract policy engine by default: the existing in-memory engine and fixture authorization contracts are reusable evidence, while the missing proof is durable, enabled production-path enforcement and cross-service behavior. The program sequence requires the exact RG row and a named production owner before drafting; the repository evidence names no production owner or production environment, so that input remains unresolved ([sequence](/home/admin/Salience/docs/superpowers/specs/2026-10-13-v4-multiplatform-autonomy-program-sequence.md:107)).

These matrix rows contain multiple gaps, and this routing increment should close only its routing/worker slice.
