## Implemented boundary

The implemented compatibility slice covers **no-effects intelligence, selected-opportunity briefs, original native intelligence schedules, no-send dummy jobs, dry creative production, governed-publication dispatch and paired native publication schedules**, using existing workflows plus canonical V4 intake/outbox/permit boundaries. The publication extension is fixture-only, zero-budget and internally controlled; it is not production dispatch, P2 artifact qualification or full RG1. General version policy, production deployment routing and external recovery remain held. See [publication qualification](legacy-publication-evidence.json).

`LegacyDispatch.submit` reuses `_request_cycle` and `_admit` inside the authenticated PostgreSQL command transaction. The original intent, admission, cycle, frozen context, operation, start outbox, canonical queued intelligence job, immutable job linkage and actor-scoped command response commit together. A failure before commit rolls them back together. Exact commands return their original disposition; changed inputs reject. Manual/event/scheduled requests coalesce by the existing business slot. A coalesced workload must retain the same actor, niche and worker queue. Adoption of an existing fixture cycle requires its untouched original pending start under a row lock; consumed or leased cycles cannot change routes. The job uses the original start trace even when an adoption request has a different trace.

Additive migration `0036_legacy_cycle_dispatch` follows `0035_parallel_agent_teams`. It guards the canonical cycle/context/operation/intent/goal/workspace/program/actor/job binding, command and schedule-plan immutability, and linked job identity. Mutable job state and output remain ordinary canonical projections. Empty rollback is supported; populated dispatch, command or schedule-plan history prevents downgrade.

## Invocation and delivery

Opt-in `V4_LEGACY_DISPATCH_ENABLED=true` requires explicit fixture mode, disabled effects, signed identity configuration and an isolated `V4_LEGACY_FIXTURE_QUEUE` beginning `salience-v4-local-legacy-`. The configured P0 profile keeps legacy dispatch disabled. The compatibility profile replaces the old intelligence router; an old unbound run body is rejected. The original control router is also replaced with canonical linked-job/dummy routes in this compatibility profile. Creative compatibility also replaces its original router with canonical linked-job routes. The default P0 profile denies publication intake because legacy dispatch is disabled there. Under the explicit no-effects fixture compatibility profile, signed `POST /v1/publications/requests` is replaced by the governed canonical fixture intake described below; this does not enable production publishers. Other legacy endpoints require their own qualification.

`POST /v1/intelligence/runs` accepts `LegacyIntelligenceDispatch.local.v1` with `goal_id`, a typed canonical `request` containing origin, expected revision, slot and idempotency key, `niche`, and `dry_run=true`. It returns canonical IDs and the committed admission disposition. `GET /v1/intelligence/runs/{job_id}` returns scoped canonical execution and dispatch states. `POST /v1/intelligence/runs/{job_id}/cancel` commits ordinary V4 closure/outbox before a worker signals Temporal. These require current `cycles:write` / `cycles:read` database grants; caller scope headers confer no authority. Reads and cancellation cannot target another workspace or an unlinked job.

`POST /v1/intelligence/opportunities/{opportunity_id}/briefs` accepts `LegacyBriefDispatch.local.v1`, adding an exact `selected_opportunity_id` to the ordinary goal/slot/niche command. Path and command must agree; the selected row must match the original workspace, program and niche. Its immutable job payload pins that selection, and the existing intelligence workflow produces the brief under the original V4 operation/permit. Native reads reject a selected row moved into another workspace after admission; database scores are encoded as typed JSON numbers at the activity boundary. Existing intelligence command fingerprints remain unchanged.

`SalienceClient(...).legacy_intelligence` exposes `submit`, `submit_brief`, `inspect`, `cancel`, `bind_schedule` and `adopt_native_schedule`. CLI commands are `content legacy-intelligence submit --command-json ...`, `brief --command-json ...`, `inspect`, `cancel --reason ...`, `bind-schedule --expected-revision ... --niche ...` and `adopt-native-schedule GOAL --command-json ...`; they use `SALIENCE_CONTROL_JWT` and the same HTTP transactions.

`python -m salience.cycles.legacy_runtime` requires `TEST_DATABASE_URL`, `TEST_TEMPORAL_TARGET`, `V4_FIXTURE_WORKSPACE`, the isolated queue and explicit no-effects mode. It constructs fixture agents internally. A separate outbox delivery lane keeps the ordinary fixture dispatcher from consuming, exhausting or observing linked legacy starts. Delivery reuses the existing bounded `LocalCycleWorkflow`, inbox ordering, frozen authority, baseline and original permit claim. The intelligence execution ID is `salience-v4-legacy-operation:{operation_id}`; its memo binds the original cycle, operation and job. Duplicate-start and cancellation readback also verify the pinned task queue. Every intelligence activity checks current frozen authority, baseline, execution deadline, stop revisions and the original unexpired claimed permit. No model/provider gateway can be injected through this worker constructor.

Start acceptance records handoff, not business completion. Recovery messages retain identity and do not launch another intelligence execution. Unknown acknowledgment or a hard exit between claim/start and acceptance holds the original claim; activity retry cannot issue a second start. This may retain work for operator reconciliation rather than automatically completing it. Cancellation before delivery creates no execution claim or child start; cancellation of an issued execution checks its original runtime type/memo and records control delivery separately from physical cancellation outcome.

## Scheduling and rollback

After source adoption for a native schedule, prepare the existing one-goal cutover, then `POST /v1/intelligence/schedules/{goal_id}/bind` with expected revision and niche before activation. The immutable schedule plan pins actor, revision, niche and worker route. Ordinary cutover activation/poll/rollback remains authoritative. Scheduled admission and job materialization share one transaction; polling can recover a committed batch whose admission rolled back. `V4_FIXTURE_AUTOSCHEDULE=1` runs the existing bounded/fair poller. Undelivered outbox, open cycles, nonterminal legacy jobs and unresolved permit liabilities hold rollback.

Optional `V4_LEGACY_TEMPORAL_SCHEDULES=true` uses `TemporalFixtureLegacyScheduleControl` for real **disposable no-effects Temporal schedules**, with an explicitly configured test Temporal target. The fixture row pins `salience-v4-legacy-fixture:{workspace_id}:{schedule_id}`. Original action type, payload workspace/program/niche/dry-run, queue and aligned interval must match. Pause precedes activation; remote readback and physical drain of old intelligence executions are mandatory. Recent actions cannot cross the first V4 slot. Database-only control cannot attest a pinned Temporal schedule.

Rollback requires the immutable bound plan. While the original schedule is paused, its action is replaced with bounded `SalienceLegacyScheduledIngress` on the pinned compatible fixture queue; its start bound is at least the canonical later slot, with an exact watermark note. Each real tick uses Temporal's scheduled-slot attributes and verifies the actual recent action's workflow ID, first execution ID and slot. Missing or fabricated scheduling attributes cannot substitute for that remote receipt. See the [Temporal schedule contract](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/workflow/schedule.mdx).

The ingress has a finite activity retry/deadline and commits no workload start itself. Admission requires current schedule/write grants, original plan/route/program, active compatible goal, no stop, completed canonical rollback and a slot strictly after its watermark. Pending rollback admits no work; V4 polling remains fenced after rollback. Original admission, job, linkage, outbox, command receipt and legacy slot progress share one transaction. Crash rolls them back together; concurrent/exact ticks recover one original response and operation. Workload execution still requires the separate canonical outbox worker and original permit. An unknown schedule update acknowledgment is reconciled through exact remote readback. After verified rollback completion, exact command replay returns the canonical receipt without another remote update. Unknown readback retains the rollback fence and may retry the idempotent schedule update; ingress cannot admit workload before canonical rollback completion.

This fixture rollback keeps the compatible ingress and intelligence worker available on its pinned queue. It does not prove routing new histories to an older binary, production schedule migration or a live provider rollback. A restored compatible worker can execute the committed outbox after ingress or worker interruption; uncertain external outcomes remain held.

After ordinary committed ordered close, the worker validates exact original workflow type, queue and memo, pins the observed run ID, and issues Temporal cancellation to that run. Cancellation acknowledgment proves control only; the canonical job becomes cancelled only after `CANCELED` terminal readback. Lost acknowledgment is read back; no second start occurs. ## Governed publication stage

`POST /v1/publications/requests` keeps the original signed publication intake route under the explicit `V4_LEGACY_DISPATCH_ENABLED=true`, `SALIENCE_DEPLOYMENT_MODE=fixture`, `SALIENCE_EFFECTS_ENABLED=false` profile. `GET /v1/publications/runs/{job_id}` and `POST /v1/publications/runs/{job_id}/cancel` read or close the original linked run through canonical cycle/job identity. The default profile remains locked down, and the original native publication schedule-creation route is not exposed as a way around canonical cutover.

A publication request carries the original goal and typed canonical request plus exact ready package, publisher account, approved publication request and budget IDs. The stage binds an immutable account mapping to the exact approved goal revision/baseline; intake and every native business activity recheck the current account mapping/grant, native profile, approval, disclosure, policy, rights, request, budget and original run identity. Account binding requires `legacy:publication` and `legacy:publication:account:<UUID>`; reconciliation has its own separate `legacy:publication:reconcile:account:<UUID>` scope. No header can grant these permissions. The internal fixture path permits only the exact fixture destination/profile with publication budget limit zero.

The canonical `governed_publication` job keeps `dry_run=false` to satisfy the existing `GovernedPublicationWorkflow` contract. Effects remain disabled: the compatible worker constructs the fixture-only adapter internally, accepts no caller-supplied provider and cannot send to a live destination; the publication budget must be exactly zero. Intake commits original intent/admission/cycle/context/operation, immutable publication-stage binding, queued job/linkage/response and start outbox in the canonical transaction. Existing operation, cycle and command identity are preserved. Migration `0040_legacy_publication_stage` adds immutable publication-stage/account/source/receipt guards after `0039`; empty rollback restores the exact earlier trigger and populated publication history refuses destructive downgrade.

The signed schedule flow first adopts the actual paired native source, then prepares the existing cutover, binds the publication plan, activates after physical drain, and uses the existing poll/rollback controls. Route surfaces are `POST /v1/publications/goals/{goal_id}/account-binding`, `POST /v1/publications/schedules/{goal_id}/adopt-native` with both `legacy_schedule_id` and distinct `publication_schedule_id`, and `POST /v1/publications/schedules/{goal_id}/bind`. SDK exposes `legacy_publication.submit/inspect/cancel/bind_account/bind_schedule/adopt_native_schedule`; CLI exposes `legacy-publication submit/inspect/cancel/bind-account/bind-schedule/adopt-native-schedule`. These are signed and use current database grants.

The native Temporal schedule identity is `publication:<publication_schedule_uuid>`; its UUID is distinct from original `job_schedules.id`. Migration `0041_native_publication_sources` stores separate immutable source, progress and V4 plan rows for that pair. Adoption reads the actual original `GovernedPublicationWorkflow` action, `:execution` action ID, exact queue, request payload, interval, future slot and recent-action history. The original database schedule payload/action are retained. Preparation pauses and reads back the original schedule, activation refuses live actions until the original activity is physically drained, and rollback records an exact watermark. After rollback, the original remote schedule executes bounded `SalienceLegacyScheduledIngress` on the pinned queue. The activity verifies its real Temporal scheduled slot/workflow/run/action readback and the exact paired IDs, then calls `admit_legacy_publication_tick`; that transaction can only commit canonical admission, original cycle/context/operation/job linkage and outbox. It never calls the old scheduled publication activity and creates no new direct job. Exact next-slot progress advances with that transaction.

Expired execution permits cannot be renewed by reconciliation. With a current exact reconcile grant, the worker revalidates the original revision/account/baseline/native authorization and reads only an already durable exact receipt; no receipt means no provider callback or second submit. Recovery remains held before status polling or business projection. A published readback during ordered post-close cancellation raises nonretryable `LegacyPublicationRecoveryHeld`; it preserves the original receipt and running liability without a canonical publication or cancellation status event, reservation settlement/release, output, or terminal success.
