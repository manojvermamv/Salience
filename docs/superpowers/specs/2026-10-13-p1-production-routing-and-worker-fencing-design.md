## Approaches considered

1. **Keep the configured queue and rely on worker startup checks.** This preserves the local single-queue setup but leaves route values mutable and does not fence duplicate owners or prove a drain. It does not meet R02/R03/R06/R08.
2. **Build a new application artifact registry and launcher.** This would duplicate the authenticated launch lock, external launcher, and 0043 floor already qualified locally, while creating a second source of artifact truth.
3. **Extend the existing lock/launcher contract with one deployment route manifest and use the named deployment platform's durable lease/fencing primitive.** This reuses the existing artifact trust boundary and keeps deployment ownership separate from business-operation identity. **Choose this approach.** If the named platform cannot provide a durable compare-and-swap lease, monotonic fencing epoch, process termination, and retained readback, production registration stays held until a separate design resolves that gap; this spec does not add an application lease registry by default.

## Route and worker ownership contract

The deployment control bundle contains one canonical, secret-free route manifest authenticated by the existing launch-lock trust digest. For each route, it records exactly:

| Field | Contract |
|---|---|
| `deployment_id`, `environment_id` | Stable identifiers for the named deployment and target environment. |
| `temporal_endpoint_id`, `namespace` | Exact endpoint/TLS identity and namespace; no hostname or namespace fallback. |
| `route_id`, `route_tuple_sha256`, `task_queue` | `route_id` is a stable UUID assigned to the route and retained in the authenticated manifest. `route_tuple_sha256` is the SHA-256 of the canonical route tuple defined below; it is evidence for the tuple and does not replace the route UUID. The queue is the exact server-side task queue used by its producers and workers. |
| `worker_kind`, `worker_build_id`, `image_sha256` | Closed worker entrypoint and exact compatibility-lane identity, including the qualified image. `legacy-fixture` is rejected in production. |
| `workflow_types`, `activity_types`, `producer_bindings` | Exact allowlists from the selected candidate and mapping from each allowed producer or persisted binding to this route. Unknown types or bindings fail closed. |
| `slots` | Finite operator-owned slot IDs. Autoscaling may use only a slot already present in the authenticated manifest; adding a slot changes the manifest digest and requires qualification. |
| `artifact_sha256` | Exact retained artifact digest from the existing worker pin. The external launch-lock digest remains the independent trust root and is captured in lease/evidence readback, not self-referenced inside the lock. |
| `compatibility_mode` | The exact Temporal server routing/versioning capability used for this deployment. If it cannot pin executions to compatible workers, require a non-overlapping drain before a different artifact takes the same queue. |

Production startup must reject missing or duplicate route entries, malformed hashes, unknown workflow/activity types, a caller-supplied queue, a route-manifest/lock digest mismatch, a development default, or any target identity that differs from the manifest. Compute `route_tuple_sha256` as SHA-256 over the canonical JSON bytes of exactly `deployment_id`, `environment_id`, `temporal_endpoint_id`, `namespace`, `task_queue`, `worker_kind`, `workflow_types`, `activity_types`, `producer_bindings`, and `compatibility_mode`, using the existing lock convention: sorted keys, compact separators, UTF-8, and one final newline. Treat workflow/activity names and producer bindings as canonical sets: sort unique type names, sort keys within each producer binding, then sort producer-binding entries by their canonical JSON bytes; reject duplicates. Exclude `route_id`, slot lists, image/artifact digests, and all manifest/lock digests from this tuple. For the authenticated manifest payload, sort the unique slot UUIDs by their canonical string form before hashing. The stable UUID `route_id` is independently assigned and appears alongside `route_tuple_sha256` in the authenticated manifest. Compute `route_manifest_sha256` over the canonical manifest payload, including the route UUID and tuple digest, and carry it in lease/readback evidence; do not embed a digest of a value inside that value. A route is not authorization to perform work; policy, effect permits, and current authority remain owned by the policy/revocation increment.

For each `(route_id, slot_id)`, the lease service records the current `owner_id` (deployment replica identity plus unique process boot ID), monotonic `fencing_epoch`, lease expiry, route-manifest digest, artifact-lock digest, build ID, and lifecycle state. Claim is one compare-and-swap operation. A concurrent second claim for the same slot loses and cannot register. Renew/release requires the exact current owner and epoch. Expiry, loss of renewal, digest drift, or a higher epoch fences new work by the old process. Lease timing is fixed in the named route manifest; renewal must occur at most one third of the lease lifetime, and the process must stop polling before that lease expires. The time source is the lease service, not a worker's local clock.

### Route-action serialization and stale-process semantics

Carrying an epoch is not a fence by itself. The named lease service must implement a versioned, linearizable `authorize_action` contract for every production permit issue, dispatch claim, and later activity that can advance an effect or perform a scoped recovery read. It validates the exact deployment/environment, route, slot, owner boot ID, epoch, route-manifest digest, artifact-lock digest, action kind, and original operation/permit identity against its current state and server time. Claim, renewal, expiry, termination, owner transfer, and `authorize_action` share one per-slot serialization order. Missing, unknown, expired, stale, mismatched, or unavailable lease state denies.

Each successful call returns one unique, one-use `route_fence_decision_id`, bound to the full tuple and short expiry. The policy-owned production transaction must consume that decision in the same database transaction as the current policy/stop check and permit/claim/action record; the IDs and digests are stored with the canonical operation. A decision cannot be reused for another operation, permit, activity, route, or epoch. The lease service invalidates an unused decision on transfer/expiry. A decision already consumed with a matching production action is one in-flight liability: the action may have reached the provider even if its response is lost, but it never authorizes another action. Such claims remain in the drain/rollback inventory until a terminal receipt or durable hold accounts for them. The production target must demonstrate that the lease service and policy transaction can meet this ordering; if it can only check at startup/poll time or pass an unverified epoch, production qualification stays `HELD`.

On renewal loss or process suspension, the worker stops polling before TTL. After it resumes, it must obtain a fresh `authorize_action` decision for the exact current epoch and pass current policy/stop checks at issue, claim, and each later action. A process paused beyond TTL, during lease-service outage, or after owner termination/transfer cannot use a prior route decision. Any previously consumed claim remains an in-flight liability and is not replayed; no new provider call may be made by the stale owner.

The launcher order is fixed:

1. Authenticate the external launcher, lock, wheel/image/runtime pins, source/import and migration inventories, and the 0043 fixture floor before importing application code, as the current launcher already does. Production registration also requires the exact later qualified production head.
2. Resolve and authenticate exactly one route and worker slot. Acquire that slot's lease with a new owner ID and epoch. A failed or ambiguous lease read denies startup.
3. Pass the route ID, slot ID, owner ID, epoch, route-manifest digest, and artifact-lock digest to the child as startup identity. The child rechecks that identity and lease before Temporal connection/registration. It registers only the allowlisted workflow/activity types on the manifest's exact namespace and queue.
4. Renew the lease while running. A renewal failure, stale epoch, route/artifact change, or lease-service outage stops new polling and closes the worker before expiry. Before permit issue, claim, and every later effect/reconciliation action, call the versioned `authorize_action` contract and consume its one-use decision in the relevant canonical transaction alongside current authority checks. Lease state itself never grants effect authority; an epoch that is merely carried as metadata is insufficient.
5. On drain, the controller first prevents new route admission using the owning policy/schedule contracts, then asks the worker to stop polling, waits for active activities to finish or persist their existing typed held/unknown outcome, shuts down the worker, and reads back the exact route, slot, lease epoch, Temporal pollers, and outstanding task/workflow state. A successor cannot claim that slot until the old process is terminated and readback shows no old owner polling or unaccounted active activity.

Worker scale-out is allowed only as additional explicitly listed slots on the same exact artifact and compatibility lane. Rolling mixed artifacts on an unversioned queue is denied. If the named Temporal service cannot keep workflow histories pinned to compatible build IDs, the deployment must stop admission, drain the old lane, and use an explicitly mapped queue lane for the new artifact. The selected server mechanism and exact queue/build IDs are part of the candidate evidence. No queue is chosen here because the initial audit has no production Temporal namespace or route configuration.

## Workflow identity, durable facts, and compatibility floor

Routing identity is transport metadata and never replaces or changes the business idempotency key. Worker restart, lease transfer, or artifact upgrade preserves the existing Temporal workflow ID and history, `CycleIntent`/cycle ID, schedule slot, operation ID, outbox message/sequence, and original authority/context bindings. Continue-As-New may advance the Temporal run ID only through the existing tested history-continuation path; it must preserve the stable workflow/cycle/operation identity and lineage. A new lease epoch must not create a new workflow, cycle, slot, or operation.

The minimum new durable facts belong in the named deployment lease service and retained deployment evidence: route/slot, owner, monotonic epoch, expiry, current state, artifact/route digests, action-decision identity, and transition/readback receipt. The application database remains the authority for canonical P1 operations, production permits/current pointers, outbox/inbox work, and publication liabilities. Policy/recovery migrations may add those source-specific business records; this routing increment does not add a second route registry or rewrite historical task queues, workflow histories, operation identities, schedules, or 0042/0043 holds. Do not synthesize route owners. The production compatibility floor is the exact authenticated migration head containing the production policy/permit, schedule binding, and recovery evidence relations, extending the current 0046 head; 0043 alone remains the historical fixture floor and cannot qualify a prior artifact to read production rows.

The exact application artifact continues to use the existing `salience.publication-worker-launch-lock.v1` trust root and `salience.publication-worker-pin.v1` pin semantics (or a reviewed, versioned extension authenticated by the same external digest). The route manifest cannot weaken any source, import, launcher, interpreter, wheel, image, or lock check. Workers that can read or write publication recovery liabilities must run an exact artifact whose authenticated migration graph retains hard historical floor `0043_complete_publication_recovery_liabilities` and matches the exact qualified production head extending 0046. An empty 0042 database, old 0042 binary, unknown revision, unpinned artifact, stale lock, changed image, unrelated migration graph, or 0043-only/0046-only production candidate is denied before worker registration. The current `182c4e43…` wheel/lock is only a retained local evidence anchor; a production candidate requires its own exact pins and cannot inherit production acceptance from that fixture.

## Drain, rollback, and restart fence

Drain is a route operation; it does not convert, stop, or inventory live Temporal schedules. The schedule-fencing spec owns schedule pause/cutover/readback and must provide an admission hold before this worker drain begins. The policy/revocation spec owns stopping new permits and reauthorization. This spec owns only worker poller ownership, active-task shutdown, lease transfer, and worker/artifact compatibility readback.

Before changing or rolling back a worker lane:

1. Record a read-only baseline of route/slot/epoch, Temporal namespace and queue, open execution/history identities, pending workflow/activity tasks, active activity identities, outbox/inbox dispatch identities, and unresolved operation/hold IDs and their canonical fingerprints. Bind the baseline to the candidate and environment digests.
2. Stop new admission under the policy and schedule contracts. Drain workers without deleting or rewriting histories, outbox claims, operation records, permits, receipts, or holds. Any unknown remote outcome remains held for the recovery spec; it is not resolved by a worker restart.
3. Read back the same route and compare all prior operation identities and immutable liability fingerprints. Every operation present before drain must remain present or have a monotonic, audited terminal disposition; a missing identity, changed original authority, missing claim/receipt, or unexplained state change blocks restart. New evidence may be appended only through its owning policy/recovery flow.
4. Before invoking a prior-code `rollback-restart`, use the externally pinned, authenticated `salience.publication-worker-launch-lock.v2` / rollback-launcher ABI with the exact workspace scope and no caller-supplied hold-ID list. The launcher invokes the recovery-owned source-discriminated complete-inventory verifier before importing or executing prior application code. It queries both `expired_permit_receipt` and `published_during_cancel` for every applicable source, validates all snapshot versions, and records per-source/per-reason counts; zero, one, or many rows are valid inventory shapes only when the complete query and all row checks pass. The pre- and post-verification inventory digests and liability fingerprints must match. Missing/NULL snapshots, omitted extra rows, changed liabilities, wrong workspace/reason, unsupported snapshot version, verifier outage, or an incomplete source query denies before `exec` and before registration.
5. Restart only a previously reviewed and qualified prior artifact that understands the exact production migration head containing the production permit and recovery records, implements the same route/policy action barriers, replays every retained history on the route, and matches authenticated lock/image/interpreter/source pins. Temporal history readback and route ownership readback must show no task or execution assigned to an incompatible worker version. An earlier artifact is not safe merely because it was deployed previously; 0042, a 0043-only artifact, or any artifact below the qualified production floor remains prohibited for production restart.

If any baseline cannot be read, any owner is missing, the lease is uncertain, any task/operation is unexplained, any liability changes, or the prior artifact fails the 0043 verifier, keep the route stopped and retain all records. This restart fence never deletes a liability or downgrades the database.

## Acceptance and evidence

Tests begin red against the named candidate and use the actual external launcher process and target deployment's no-effects route. Unit-only tests do not qualify registration or production routing.

1. **Exact route admission:** unknown/missing namespace, queue, producer binding, worker kind, activity/workflow type, manifest digest, or fallback/default configuration is denied before Temporal connect or worker registration. A route pointing at a different environment fails even if its queue name matches.
2. **Artifact and floor denials:** mutate the wheel/image digest, independent lock digest, launcher/interpreter/runtime pin, source/import inventory, or migration inventory; require denial before application import/registration. Test empty 0042, an earlier revision, unknown revision, branched/ambiguous history, and an unqualified descendant. Exact 0043 passes only the historical fixture-floor check; production registration requires the exact qualified descendant extending 0046 and all lock checks.
3. **Lease ownership and stale fencing:** race two launches for the same route/slot; exactly one CAS claim and registration succeed. A duplicate owner, expired lease, wrong owner, stale epoch, route-manifest drift, artifact mismatch, or delayed renewal cannot register or continue polling. Exercise `authorize_action` at issue, claim, and every later action boundary against lease-service outage and concurrent owner transfer. Pause a real process beyond TTL, terminate/transfer its owner, then resume it; it must fail before obtaining a fresh decision or making another provider call. Count any earlier consumed action as one unchanged in-flight liability.
4. **Restart identity:** stop a worker with an existing workflow and pending idempotent operation, restart the same compatible artifact under a new boot ID/epoch, and prove history replay resumes the same workflow ID and preserves the same cycle/slot/operation/outbox identities. Verify no duplicate Temporal start, provider request, permit, or cycle is created.
5. **Drain and readback:** start active and queued work, hold new admission through the owning policy/schedule interfaces, drain the worker, and read back zero old pollers/active tasks, released prior lease, accounted queued work, and unchanged or explicitly appended terminal operation evidence. A stale process or unaccounted task prevents successor registration. Repeat with worker crash, renewal loss, and delayed shutdown.
6. **Rollback and unchanged liabilities:** capture the route and complete source inventory, then test changed liability, missing/NULL-v1 row, changed workspace, an omitted extra hold hidden by a partial caller list, unsupported snapshot version, verifier timeout, and prior artifacts at 0043-only and below the exact production floor. Each must preserve database/history state and deny before prior-code registration. Exercise zero, one, and many rows for each reason independently, plus mixed fixture/production sources. Both reason queries must execute even when a reason has zero rows. A candidate prior artifact with exact authenticated production-floor pins, complete unchanged inventory, unchanged operation identities, and compatible histories may restart; read back the same evidence after restart.
7. **Named-environment run:** on the exact named target, retain initial and final route/lease/Temporal readbacks, owner approvals, deployment/image/artifact/lock/source/migration digests, exact commands and exits, test reports, operation/liability fingerprints, and independent reviewer disposition. Use secret-free evidence with the exact candidate commit and environment-manifest digest. No fixture result transfers to production.

Required logs/metrics include route and deployment IDs, namespace/queue identity, slot, owner boot ID, fencing epoch, lease age/renewal outcome, build ID, short artifact/lock digests, registered workflow/activity set, poller/active-task counts, drain duration, pending-operation count, and typed denial reason. Alert on unknown route/artifact, stale or duplicate owner, renewal failure, an old poller after drain, an unsupported schema, incomplete rollback readback, or route drift. Do not log credentials, tokens, full connection strings, signed URLs, or secret values.

Each acceptance result records status `PASS`, `FAIL`, `NOT RUN`, or `HELD`, exact candidate/artifact/environment, owner, evidence path/digest, freshness, remaining dependency, and mapped requirement. Any non-PASS, stale or mismatched evidence keeps the mapped rows HELD and keeps P2 blocked.

## Explicit exclusions

- Production enablement, effect credentials, provider calls, release approval, RG0/RG1 closure, P2 entry, or `main` merge.
- Live Temporal schedule inventory, schedule creation/pause/cutover/stop/rollback, schedule slot conversion, or watermark semantics; those belong to the live-schedule spec.
- Recovery-worker business logic, remote provider reads, external alert delivery, reconciliation, escalation, or resolving unknown liabilities; those belong to the recovery/alerts spec.
- Policy engine design, cross-service revocation semantics, account/provider approval, or effect-permit authority; those belong to the policy/revocation spec.
- New generic worker framework, artifact registry, launcher, queueing platform, dynamic capability/P5 routing, arbitrary task-queue selection, or support for new platforms.
- Application schema/backfill unless a separate review establishes that a durable business fact is essential. Deployment lease facts remain in the named platform's control plane and its retained readback.
