## Intent, goals, and exclusions

Provide one immutable, independently checked acceptance package for each of the 22 in-scope rows. Every row must identify its exact final candidate, deployment, environment, account or an owner-approved reason why account scope does not apply, accountable human, authorized operator, independent reviewer, prerequisites, executable procedure, raw result, status, evidence URI and digests, freshness bound, and rollback or explicit no-mutation record.

The package makes it possible to distinguish external production acceptance from local tests, CI, formal approval, and historical evidence. It preserves failure and uncertainty as blockers. It never enables production effects, declares a release, marks a requirement passed by itself, or substitutes for the final audit.

### Approaches considered

1. **Extend the existing release and matrix status fields.** Rejected as the acceptance contract: they are useful status summaries but do not contain per-row commands, operator authority, raw results, rollback readback, or evidence freshness.
2. **Use one signed run manifest with an immutable package per row (selected).** One manifest binds the exact candidate, deployment, environment, and acceptance run; each row package binds its own account/resource scope and procedure. This keeps evidence independently inspectable while avoiding evidence transfer between rows or scopes.
3. **Create a new acceptance database or application ledger.** Rejected for this increment. No durable application fact requires a new database table; an immutable evidence bundle and repository index are sufficient. A later implementation proposal must prove a missing durable fact before proposing a schema change.

### Scope and exclusions

This design covers external acceptance of the mapped RG0/RG1 requirements, package integrity and freshness, safe rollback evidence, and a separate final audit handoff. It can consume safe, explicitly authorized read-only probes and bounded no-effect canaries. Any production deployment, schedule, identity, credential, retention, or alert mutation still requires the normal change authorization and the owning increment's procedure.

The package does not grant production authority, turn on effect dispatch, create or spend a publication budget, send a real provider effect, accept P2 provider qualification, merge code, change branch protection, or release RG0/RG1/P2. It does not authorize live probes now: the audited host has no production target or named operators. It does not rewrite historical evidence or make fixture, CI, formal-approval, or earlier-candidate results count as external acceptance.

## Package binding and row record

One acceptance run has a cryptographically hashed, append-only `manifest.json`, 22 row records under `rows/<row-id>/`, and an artifact digest index. The proposed evidence bundle location is `artifacts/v4/p1-rg0-rg1-external-acceptance/<run-id>/`; if raw material requires restricted retention, it may live in an approved immutable evidence store, with the exact URI and SHA-256 recorded in the repository index. A missing URI, mutable-only location, or missing digest is a blocker. Secrets, tokens, private keys, and raw sensitive payloads are never retained; redacted evidence is hashed after redaction, and the redaction method is recorded.

The manifest and every row record must contain the following fields. Fields may not be blank or silently inherited from a different run.

The run manifest binds one exact final candidate, one deployment, and one named environment. Each row's account/resource scope is exact within that environment and is not transferable to another account, tenant, workspace, provider, repository, namespace, or resource. If one requirement spans multiple accounts or targets, each is enumerated as a separate child check under the same row and all must pass. The final audit must verify every child scope against the applicable requirement.

Freshness limits are not invented by this spec. Before execution, the relevant accountable owner must set a numeric maximum age in a versioned, reviewed target-operations policy for each mutable observation class (identity/grant, repository protection, worker route, schedule inventory/readback, alert destination, storage/restore configuration, and similar). Missing, expired, or unapproved limits make the affected row `HELD`. Candidate artifacts are immutable. Every mutable target is read at the beginning and end of the run, but comparison depends on the declared observation class:

- **NO_MUTATION:** the procedure declares no target change. Beginning and ending state digests must be equal. Any unexplained difference is unplanned drift and invalidates the affected evidence.
- **Planned authorized transition:** before the command, pin an authorized change/ticket, exact target scope, expected transition, and expected pre/post versions. Preserve both readbacks and the command/actor receipt. The independent reviewer compares the observed transition to that predeclared contract and verifies the final state against its fresh, approved digest. An exact planned transition is the result under test; it does not invalidate its own evidence.
- **Subsequent or unplanned drift:** any change outside the predeclared transition, to a different target/scope, or after the final reviewed readback invalidates the affected observation and its dependency closure. Rerun affected procedures after the state is reviewed again; never restore a revoked/rotated credential or policy revision to recreate the beginning digest.

## Status and evidence rules

Each required check and row uses exactly one of `PASS`, `FAIL`, `NOT RUN`, or `HELD`; freshness is a separate `CURRENT`/`STALE` field, and scope match is a separate exact-match boolean. `PASS` requires all required child checks to pass on the declared scope, all prerequisites and human roles to be present, current evidence, a verified rollback, a verified predeclared planned transition, or justified `NO_MUTATION`, and an independent review. An expected denial in a negative control is a passing result only when the raw result proves the prohibited action did not occur.

- `FAIL`: a required assertion was executed and the control or invariant failed. Preserve the observed result; do not relabel a failure as held because it is inconvenient.
- `NOT RUN`: the required procedure did not execute or has no raw result.
- `HELD`: execution is unsafe or cannot be interpreted because a prerequisite, owner, authority, target, rollback proof, or exact scope is absent, ambiguous, or unresolved.
- `STALE`: the required max age is exceeded, the source state differs from its final reviewed digest because of unplanned/subsequent drift or an unverified transition, or the result was not captured against the final candidate/deployment/environment. An exact planned transition is not stale merely because its pre-state and final state differ. A stale result cannot be `PASS`; classify the row `HELD` pending a rerun.

Any `FAIL`, `NOT RUN`, `HELD`, stale observation, candidate/deployment/environment/account mismatch, missing named owner/operator/reviewer, missing digest, or unresolved rollback keeps the applicable RG0/RG1 entry blocked and P2 blocked. The package checker may report a machine-readable `NO_GO`; it cannot declare a gate `GO`.

Evidence classes remain separate:

| Evidence class | What it can establish | What it cannot establish |
| --- | --- | --- |
| Local fixture | Behavior exercised against the named local fixture candidate/environment. | Production identity, target configuration, live schedule/worker state, remote alert delivery, production acceptance, or formal approval. |
| CI | Checks run by a named workflow on one exact commit, including workflow/job conclusions and raw artifacts. | Production deployment or account state, formal human approval, or live external behavior. |
| Formal approval | Required independent PR/release approval and current repository protection readback for the exact candidate. | Runtime production acceptance or provider qualification. |
| External production acceptance | The row-specific external observation on the exact deployed candidate/environment/account scope. | Formal approval, P2 effect approval, or the final gate decision. |
| Historical candidate | A result for the exact earlier candidate and scope recorded at the time. | A result for any successor commit, deployment, account, environment, or changed target state. |

CI success, formal approval, and external acceptance are three different records. R01's repository-enforcement proof must include current read-only branch-protection and required-check readback plus the exact candidate's CI record; the approval artifact must separately identify the required human PR reviewer and current approval state. A successful workflow is never treated as PR approval, and approval is never treated as deployment acceptance.

## Execution, observability, and rollback sequence

When a later approved run is authorized, execute in this order:

1. Freeze the candidate commit/tree, signed artifact set, deployment ID, environment manifest, account/resource inventory, migration head, effect-disabled state and zero publication budget. Hash and sign the run manifest before row procedures start.
2. Confirm every required bounded increment is implemented and accepted at its own exact candidate/environment scope; collect its prerequisite evidence references. Assign and verify each named owner, operator and independent reviewer. Pin reviewed runbooks and numeric freshness limits. Missing input stops execution before any target action.
3. Capture beginning readbacks for mutable state, record exact commands/API requests and principals, and run only the row's authorized no-effect/read-only/synthetic procedure. Preserve raw redacted output, error codes, trace IDs and external receipt IDs as they occur.
4. Capture independent readbacks and observability for each row: relevant structured events, health/latency or lag measures, denied/allowed counts, remote delivery/readback, unresolved work/liability count, and alerts. Record alert delivery separately from human acknowledgement and from gate approval. Missing required telemetry or an unexplained target change is a hold.
5. Verify the row's predeclared planned transition, run the separately authorized restoration when its contract requires one, or record verified `NO_MUTATION`; capture final-state readbacks, liability inventory, and route/schedule/identity/security state. A rollback timeout, unknown remote response, active liability, unplanned drift or missing acknowledgement leaves the row `HELD`. Permanent revocation tests finish with the revoked identity still revoked and current denial read back.
6. Hash the immutable evidence bundle, have the independent reviewer verify hashes, scope, freshness, expected outcomes and rollback, then sign the row package. Append a new run for any rerun; never overwrite a prior package.

Observability must make the acceptance run correlatable without leaking secrets: UTC timestamps, actor identity, command/request IDs, trace IDs, candidate/artifact digest, environment and account aliases, route/schedule/operation IDs, bounded reason codes, and external response IDs. Store metrics/logs with access and retention controls; do not use personal, tenant, account, or operation identifiers as unbounded metric labels. Alert on stale/incomplete inventory, scope drift, missing owner/reviewer, failed rollback, unknown remote result, failed delivery/acknowledgement, or unresolved liability. An alert documents response; it never clears a hold or grants approval.

Rollback evidence is an acceptance prerequisite, not a cleanup note. For read-only procedures, the row must include a signed `NO_MUTATION` record and matching beginning/end target digests. For a planned mutation, preserve the pre-state, approved change ticket, operation ID, exact expected transition, actor receipt, final-state readback, compatible artifact/worker/schedule floor, and unresolved-liability inventory. If a test revokes or rotates a credential, keep that revocation in force and prove denial from the new version; rollback restores only non-security test configuration when separately authorized. Never restore the old credential or policy revision to force digest equality. An approved state restoration is a separately declared transition with its own command and readback. If rollback cannot be proved, stop forward work and keep the environment fenced. Do not resume a prior worker/schedule while policy, stop, remote outcome, or business liability is unresolved.

## Invalidation and final-audit handoff

Evidence is invalidated by any change to the source commit/tree, build artifact, lock/provenance, deployed service set, deployment ID, migration head, environment manifest, region/account/tenant/workspace, provider or repository identity, Temporal namespace/schedule inventory, worker route/artifact floor, policy/grant/approval/secret version, retention/alert destination, runbook/checker version, or any observation beyond its owner-approved freshness limit, except for the exact transition predeclared and verified as that procedure's mutation result. The final reviewed state after a planned transition becomes the comparison point for later observations; any subsequent or unplanned change from it invalidates affected evidence. A common manifest change invalidates the whole run. A row-specific change invalidates that row and its dependency closure; the final audit must re-evaluate every affected row. A planned revocation may make dependent evidence require a fresh procedure, but it does not erase the row's evidence that the revocation and denial occurred. Reruns receive new IDs and preserve invalidated originals with their reason and digest.

The package checker must refuse to combine child evidence with differing candidate, deployment, environment, account/resource scope, or runbook version; it must not copy a prior PASS forward. The final audit independently reads the 22 row records, re-verifies hashes and currentness, reconciles each against `p0-release.json`, `p1-qualification-matrix.json`, the required increment evidence and exact deployment readbacks, and records the separate final disposition. Only that final exact-candidate/environment audit may declare the applicable entry conditions passed. Any failed, missing, stale, held, mismatched or ownerless row blocks P2.

## Package/checker acceptance tests

These are acceptance tests for the future evidence-package/checker implementation. They do not authorize implementation now and do not replace the runtime acceptance procedures above.

1. `test_package_requires_exact_candidate_tree_artifacts_deployment_and_environment`: missing/short commit, artifact digest, deployment ID, environment digest, or migration head is rejected.
2. `test_package_requires_exact_row_set_once`: the five RG0 and 17 P1/RG1 IDs appear exactly once; missing, duplicate, unknown, or wrongly gated IDs fail validation.
3. `test_each_row_requires_named_authorized_owner_operator_and_independent_reviewer`: absent names, role-only placeholders, expired scope, reviewer/operator identity collision, or unverified authorization cannot pass.
4. `test_procedure_is_pinned_and_executable`: no runbook URI/digest, tool version, exact argv/API request digest, expected predicate, raw result URI or command/request ID means `NOT RUN` or `HELD`.
5. `test_raw_results_and_rollback_are_hashed_and_referenced`: missing/mismatched SHA-256, absent independent readback, absent verified rollback/planned-transition record, or absent explicit `NO_MUTATION` invalidates the row.
6. `test_scope_transfer_across_fixture_ci_commit_environment_account_is_rejected`: fixture output, CI, formal approval, historical candidate, other environment, target, account, tenant, namespace, or resource cannot satisfy an external row.
7. `test_ci_formal_approval_and_external_acceptance_remain_distinct`: CI success cannot satisfy the approval or production acceptance fields; PR approval cannot satisfy external runtime acceptance.
8. `test_fail_not_run_held_stale_or_scope_mismatch_blocks_package`: each negative status, stale limit, false scope match, missing owner, or unknown result returns `NO_GO` and never normalizes to `PASS`.
9. `test_missing_or_unapproved_freshness_limit_holds_mutable_evidence`: an unset, nonnumeric, expired or unapproved maximum age rejects the row.
10. `test_planned_revocation_with_verified_final_denial_passes`: a predeclared grant/credential revocation with matching command receipt, expected pre/post versions, fresh independent final readback, and denial evidence remains current; the checker does not invalidate the mutation the procedure was designed to prove.
11. `test_unplanned_or_subsequent_revision_change_fails`: an unapproved change, change outside the planned scope, or later revision drift from the final reviewed state marks affected evidence stale and blocks the package.
12. `test_no_mutation_requires_equal_start_and_end_state`: a procedure declared `NO_MUTATION` passes only when beginning/end target digests match; any changed state fails or holds according to whether the executed assertion failed or cannot be interpreted.
13. `test_revoked_credentials_are_never_restored`: rollback/evidence validation rejects any attempt to restore the old credential or policy revision to force equality; a revoked credential stays revoked and denial is proven under the current version.
14. `test_run_invalidation_is_append_only_and_transitive`: candidate/common-manifest changes invalidate every row; unplanned row-specific scope changes invalidate the row and dependent rows; rerun creates new immutable run IDs without editing old hashes.
15. `test_negative_controls_pass_only_on_proven_denial_and_zero_effect`: a control passes only with raw deny evidence and independent zero-call/effect readback; missing telemetry or ambiguous count is held.
16. `test_package_cannot_enable_production_or_release_a_gate`: effect state must remain disabled and budget zero; the checker emits evidence disposition only, never a production-enable, RG0/RG1 GO, merge or P2 authorization.
17. `test_final_audit_is_separate_and_rechecks_every_row`: a complete package does not itself set gate state; final audit must independently reconcile all 22 current rows and retain any blocker.
18. `test_rollback_requires_pre_state_action_and_exact_post_state_readback`: a declared rollback with an unknown remote result, mismatched deployment/route/schedule digest, unresolved liability, or missing owner/reviewer remains `HELD`.
19. `test_observability_artifacts_are_correlated_and_secret_free`: command/request/trace IDs, required metric/log readbacks, alert receipt and human acknowledgment bind to the run while secret scanning finds no credential or token value.
20. `test_default_package_adds_no_application_migration_and_excludes_later_phases`: the default evidence index/package changes no application schema or fixture guard and cannot claim P2 provider effects, later-phase record families, production enablement, or gate release.

## Migration, rollback, and implementation boundary

No application migration is needed by default. Keep packages as immutable external evidence plus a small repository index containing run ID, exact candidate/deployment/environment bindings, row status summaries, URI and hashes. If an implementation later demonstrates that an existing immutable artifact store cannot retain a required acceptance fact, stop and write a separate bounded migration design; do not add tables or relax fixture guards as part of this spec.

No implementation is authorized here. Production is disabled, fixture publication budget remains zero, and the initial host has no production target, account or named owners. The external procedures cannot be executed until the relevant bounded increments, target-specific runbooks, numeric freshness rules, approvals, owners and exact final deployment exist. Rollback preserves immutable evidence and liabilities; it never rewrites a historical row or treats restored code/configuration as proof that an external operation did not occur.
