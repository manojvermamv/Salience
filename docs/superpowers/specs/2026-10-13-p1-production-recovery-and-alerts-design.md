## Intent and boundary

Provide production-owned recovery for uncertain or failed P1 operations without repeating an uncertain effect. A recovery worker may read the exact remote object belonging to the original operation, append what it observed, and notify the assigned owner and approved on-call path. It cannot submit, cancel, publish, settle, release, approve, or resolve the operation by itself.

Reuse the existing immutable publication-hold evidence and exact replay behavior, plus the typed recovery-case and wait contracts. A hold remains held and its liabilities remain intact while evidence is gathered. An alert acknowledgment proves only that an authorized person received the notice; it never approves work or clears a hold.

This increment advances only its mapped recovery and alert obligations. It does not qualify production policy, worker routes, live schedules, or external RG0/RG1 entry. Production effects remain disabled until their separate entry conditions and authorizations are met.

## Goals and exclusions

The design must bind every recovery observation and alert to one exact workspace/tenant, target, source case or hold, context, original operation ID, request fingerprint, and current authorization decision. It must preserve unknown outcomes and their liabilities, keep recovery retries bounded, retain durable evidence after restart, and make alert delivery and human acknowledgment independently inspectable.

It excludes new provider effects, new operation identities, blind retry or cancellation, implicit provider/account selection, arbitrary remote search, automatic case or hold resolution, treating an alert as approval, weakening fixture guards, modifying live schedules, or adding a new platform. Policy and revocation semantics belong to the policy increment; worker registration, leases, artifact floors, drain, and restart compatibility belong to the routing increment; schedule inventory and fencing belong to the live-schedule increment; row-level external acceptance belongs to the external-acceptance increment.

## Existing contracts to preserve

- `v4_legacy_publication_recovery_holds` records immutable fixture holds by original operation ID and one of the two reasons `expired_permit_receipt` or `published_during_cancel`. It stores request, receipt, and liability fingerprints and the full liability snapshots. `publication_recovery.record_publication_recovery_hold` serializes concurrent insert/replay, returns the same hold for an exact replay, and rejects changed evidence. Migration 0043 adds the exact v1 liability baseline; the receipt and progress bindings remain fixture-specific and do not authorize production use of fixture receipts.
- `v4_recovery_cases` owns the existing typed states and bounded owner/deadline/action fields. A cycle reconciliation case uses kind `reconciliation` and failure class `unknown_effect`; case commands retain the original context and operation. Existing case transition guards remain authoritative. Do not add a generic state transition or reopen a closed cycle to make publication-hold handling fit a case API.
- `v4_runtime_waits`, `v4_case_notifications`, and `v4_case_acks` retain the existing case deadline, escalation, and acknowledgment semantics in fixture qualification. `RuntimeWaits`, `FixtureWaitDriver`, and `FixtureNotificationSink` are explicitly fixture-only. Their database acceptance is not external delivery or human acknowledgment. Production work reads canonical case/intent revisions and deadlines through the production controller below; it never launches fixture timer or notification routes.
- The fixture publication-hold verifier checks fixture rows only. The recovery increment owns a separate read-only source-discriminated verifier that inventories fixture and production sources and every supported snapshot version. The routing increment owns the authenticated, versioned launcher ABI that runs this verifier before prior-code execution. Migration 0043 remains the fixture compatibility floor; production restart requires the exact qualified descendant that contains and understands all production permit, work, event, and command records.

`published_during_cancel` refers to a closed, cancelled cycle. Existing `open_case` correctly rejects opening a new case for a closed cycle. Keep that rule. The production immutable hold row binds the original operation and evidence without manufacturing a case, reopening the cycle, or mutating the hold. `expired_permit_receipt` has the opposite legal state: the source cycle is still open because no durable receipt proves completion. Its production immutable hold is allowed only for an open cycle and may link to an already existing matching typed case; it never closes the cycle to manufacture the hold. Other eligible open-cycle cases continue to use the existing typed case as their business state machine. The fixture hold row is never adopted as a production hold.

## Approaches considered

1. **Promote the fixture worker and notification sink into production.** Rejected because the worker rejects production mode, the provider is a mock, and the notification sink records only database fixture acceptance. Removing those guards would conflate fixture and production trust boundaries.
2. **Create a parallel recovery-case, scheduler, and notification platform.** Rejected because it would duplicate the current case, wait, operation, and worker-routing contracts and create competing state for the same liability.
3. **Keep existing cases and holds canonical, add a small production recovery evidence boundary, and use the separately qualified worker route and external channel.** Selected. Existing cases own eligible open-cycle transitions; immutable holds own publication close-race evidence. A narrow production work binding is needed to attach owner, exact source, and external read/alert history to either source without changing either source's state machine.

## Recovery identity and additive data

Add one additive migration after the current 0043 floor. It creates two production-only relations; it does not alter or backfill fixture hold or notification rows.

### `v4_production_recovery_work`

One immutable row represents one production recovery subject. Create it atomically with the source binding and first alert-intent event. An exact uniqueness conflict returns the existing work ID; any mismatch fails closed. At rollout, enumerate eligible existing cases, holds, and pre-admission intents and adopt them with exact source readback before starting the worker. It contains:

| Field | Contract |
|---|---|
| Stable work ID and source | Unique row ID and exactly one source discriminant: `cycle_case`, `production_publication_hold`, or `pre_admission_intent_case`. `cycle_case` references one eligible existing `case_id`; `production_publication_hold` stores the immutable source hold described below; `pre_admission_intent_case` references one original intent and eligibility revision before any cycle exists. |
| Canonical scope | Workspace/tenant, goal, intent, owner, source revision, deadline, and source fingerprint. For `cycle_case`, cycle/context/operation are non-null and match the canonical case. For `production_publication_hold`, cycle and original operation are non-null and the row preserves the typed reason, request fingerprint, remote identity/observation fingerprint, owner, liability snapshot version, full canonical liability snapshot, and liability fingerprint. For `pre_admission_intent_case`, cycle, context, operation, and remote target are all NULL by design; the exact intent, eligibility revision, admission disposition, due/expiry deadline, and owner are required. Those NULLs are legal only for this source discriminant. |
| Ownership | Original case/operation owner plus a named production recovery owner. A changed owner requires a separately authorized, append-only assignment event; it cannot rewrite the source record. |
| Target | Exact provider/account alias and resource identity, represented by secret-free IDs or digests for cycle cases and publication holds. These values are NULL only for `pre_admission_intent_case`, whose provider-read permission is always denied. The target is immutable for every applicable work item. |
| Deadlines and policy | The case deadline/revision at adoption for a case source, or a target-specific approved recovery deadline for a hold source; initial policy and recipient-profile revision references. No implementation-selected default. Current decisions and later approved policy/owner changes are appended to the event ledger without replacing the work row. |
| Identity fingerprint | SHA-256 over the source discriminant, original intent/case/hold identity, source revision, original operation when present, reason when held, exact target when applicable, source owner, and deadline at adoption. Exact repeated adoption returns the same row; a changed source/revision/operation/target conflicts. Policy revision or authorized owner changes append events and do not create another work identity. |

For a `cycle_case` source, the production row is only an immutable binding to the existing case and its original operation; that case remains the business state machine. A `production_publication_hold` row is itself an immutable hold fixed to `held`. Its only valid reason/state pairs are `expired_permit_receipt` with an open cycle (`cycle.state <> 'closed'`) and `published_during_cancel` with a closed/cancelled cycle (`cycle.state = 'closed'`). The expired-permit form may link to an already existing matching case but may not create one solely to represent the hold. It carries the exact original operation, canonical request/remote evidence, and complete versioned liability snapshot. Snapshot computation names every liability family and uses canonical ordering/hash rules. The existing `salience.publication-liability.v1` 21-key set is the minimum contract; an unsupported/incomplete version rejects insertion and blocks restart. The `pre_admission_intent_case` row preserves a deferred/review-required intent before cycle allocation. It has no operation or provider target and must never enter provider reconciliation. Constraints enforce source-discriminant/nullability rules, same-workspace bindings, source operation equality where operation exists, unique work per source/revision, immutability, and no fixture-to-production adoption. Existing production sources, if any, are adopted only after an authorized exact inventory and owner assignment; fixture rows cannot be backfilled as production work. No recovery work row means the worker must hold the source and report an inventory gap, not skip it.

### `v4_production_recovery_events`

An append-only ledger records remote observations and alert lifecycle evidence for a work item. Its minimum fields are stable event ID, work ID, unique idempotency/event key, typed event kind, UTC observation time, actor or authenticated worker route/slot/fencing epoch, current policy decision reference, allowlisted bounded payload, and canonical payload SHA-256. Event kinds include remote-read observation, alert intent, delivery attempt, delivery receipt, acknowledgment, retry scheduled, escalation, owner assignment, owner unavailable, stop/revocation fence, and held conflict. SQL guards reject update/delete, cross-work scope, duplicate event keys, unrecognized event kinds, malformed hashes, and unapproved payload keys. A secret-redaction check rejects unsafe content before persistence.

The alert intent is unique by work item, case revision when applicable, and severity/escalation level. Its stable provider idempotency key is derived from the immutable event identity. A transaction locks the work row, checks the event ledger, and appends one claim/attempt event with a finite claim expiry before network I/O. A second worker cannot claim the same active attempt. The state is derived from the event ledger; no mutable delivery record may overwrite accepted, failed, or acknowledged history.

The work row is the only new identity binding; when its source is a production publication outcome, that row is also the immutable production hold. The event ledger is the durable evidence and bounded alert outbox. Existing `v4_case_commands`, `v4_case_events`, and `v4_case_archives` remain the idempotency, transition, and archive records, with the production controller's typed authorization reference recorded in the command result/event. The new relations are required because the current hold schema is fixture-bound, current case events cannot represent a publication hold, and the existing notification delivery projection is fixture-only. Do not add a second general recovery state machine or alter an immutable source case or hold.

### Source discriminants and valid state/reason pairs

`cycle_case` requires a current, nonterminal `v4_recovery_cases` row whose cycle remains open and whose context/operation/owner match the work binding. `production_publication_hold` requires an immutable complete snapshot and exactly one of the two state/reason pairs: (1) `expired_permit_receipt` and open cycle, with expired original permit and accepted/processing progress but no durable receipt; or (2) `published_during_cancel` and closed/cancelled cycle, with the exact cancellation race evidence. A wrong reason/state pair, missing source, changed operation, or incomplete snapshot is rejected. These holds remain held and immutable even when a later read observes terminal success.

`pre_admission_intent_case` is bound to one `v4_cycle_intents.id`, its current `eligibility_revision`, matching `v4_admissions.disposition`, canonical `due_at`/`expires_at`, goal/workspace, and accountable owner. `cycle_id`, `context_id`, `operation_id`, and provider/remote target must remain NULL. It has no permission to perform any provider read; only an authorized production intent-wake command may recheck eligibility and deadline. A successful current admission may allocate the canonical cycle/context/operation once through the existing admission path, after which a new `cycle_case` work binding may be created if recovery is required. No code may fabricate an operation merely to satisfy recovery fields.

## Production case-command and deadline controller

The recovery increment owns one narrow production command boundary around the existing typed case, admission, terminalization, and archive rules. Name it `ProductionRecoveryCaseController`; it is an internal service interface, not a second case state machine. It shares the canonical `v4_recovery_cases`, `v4_cycle_intents`, `v4_admissions`, `v4_cycles`, `v4_case_commands`, `v4_case_events`, and `v4_case_archives` records. It retains their revision checks, allowed state transitions, identity joins, owner binding, deadline rules, action limits, terminal-disposition check, retention fields, idempotency, and no-reuse rule. The production controller has a separately scoped DB role and must pass current policy/stop/revocation, route-fence, stage authority, and exact approval checks before its command transaction. It does not call the fixture-only `CycleGovernance` public endpoints or use fixture account/purpose values; all fixture API, timer, and notification routes remain disabled for production. The migration adds only the narrow production authorization checks needed to admit this typed source path while leaving fixture guards and fixture assertions unchanged.

The read/reconciliation worker remains read-only with respect to business state. It may append a safe remote observation or alert event, but it cannot resume a workflow, approve a case, suspend a case, terminalize, or archive one. Those actions require a separately authorized human/service command through `ProductionRecoveryCaseController`, with a stable idempotency key, exact source and expected revision, policy/stop/route decision IDs, and immutable command receipt. A review approval must be the current policy-owned, operation/intent-bound production approval; `v4_case_reviews` fixture account/purpose rows cannot authorize a production resume.

The deadline controller reads canonical case and intent revisions/deadlines and derives deterministic wake IDs from `(source_discriminant, source_id, source_revision, due_at, action_kind)`. A production wake is deduplicated in `v4_production_recovery_events`; it never dispatches `v4_runtime_waits`, `FixtureWaitDriver`, `v4_case_notifications`, or `FixtureNotificationSink`. On due case work, it locks the exact case revision and may issue only the existing deadline suspension/escalation transition when that case state and action bound permit it; otherwise it records an obsolete/held wake and leaves the case intact. It may not convert `reconciling` or `rework_due` into retry. On a pre-admission intent, it checks the exact eligibility revision, deadline, expiry, goal/stop state, and current authority before calling the canonical typed wake/admission path. A stale revision, existing cycle, expired intent, stop, revocation, exceeded wake limit, or authority outage creates a held evidence event and no new cycle. A successful admission is the first point at which the canonical path may allocate a cycle, context, and operation.

Permitted resume paths remain the current typed stage-specific paths only: a matching, current human approval and case revision can move an eligible case to the existing `retry_due`/`resolved` state; the owning workflow then performs fresh stage authorization and obtains a new permit before any forward effect. Unknown remote outcome, unresolved liability, stale context, stop, or revoked authority cannot resume. Terminalization requires a committed terminal business disposition for the same original operation. R35 archive uses the existing immutable `v4_case_archives` row only after the case is terminal and the canonical terminal disposition is present; reason, evidence digest, actor, and `retain_until` are bound, duplicate commands return the same archive, changed requests conflict, and the archived identity can never be reused. Neither a deadline wake nor an alert acknowledgment can terminalize or archive.

The controller and timer are qualified with fixture routes disabled. Tests exercise production principals and command records against the real typed source rows, while asserting the existing fixture guards still reject production identities. No generic retry state, new case state machine, replacement intent/operation, timer database, or separate archive ledger is introduced.

For rollback, downgrade refuses to remove any work or event row or production-authenticated command result. The additive migration adds the exact source-discriminant and snapshot constraints, append-only event checks, narrowly scoped production command authorization for existing typed state transitions/archive, and grants only to the production controller. It does not make fixture routes callable in production or relax fixture trigger predicates. PostgreSQL acceptance covers production open-cycle and closed-cycle hold inserts, operationless intent work, production case commands and archive receipts with fixture routes disabled, exact replay/conflict, action/deadline limits, and rejection of production principals through fixture endpoints. No destructive rollback, hold deletion, liability rewrite, or backfill from fixture evidence is permitted.

## Production worker and trust boundary

The worker is a recovery activity on an exact route supplied by the production-routing specification. That specification owns worker registration, route/slot lease, fencing epoch, artifact pin, process drain, and compatible restart. This design owns only recovery behavior after a worker has authenticated its route. Unknown, duplicate, stale, or below-floor workers are denied before registration by the routing contract.

Use separate short-lived, read-only provider authority for remote reconciliation and a separately scoped alert-send/acknowledgment authority. Bind each credential reference to one named environment, account, provider, and resource set. No recovery credential may submit, cancel, update, list broadly, or access another account. Never persist secret values, tokens, raw provider payloads, signed URLs, or full connection strings.

Before each remote read, alert send, and acknowledgment write, recheck current stop and relevant policy/revocation state through the policy contract. A policy outage, stale policy revision, revoked grant, or stop blocks a new provider read or business action. A provider read proceeds only under the separately scoped reconciliation grant allowed by R18. Alert delivery and acknowledgment use independent, narrow communication permissions; an effects stop does not grant them, and they continue only if their own current policy checks pass. A policy outage with no separately approved outage-safe communication authority leaves the alert intent held and visible. If revocation races an already-started GET, the worker may retain only the safe result digest with the exact grant revision under which it began; it may not use that result to transition a case, resume a workflow, or authorize any effect. A stopped or revoked worker may not extend its claim or start another read. Existing liabilities and alert intents remain durable.

## Remote-read reconciliation contract

Every read targets one exact original operation. It carries the original operation UUID, original provider idempotency key, account/tenant identity, resource or remote ID already bound to that operation, request fingerprint, and the current narrowly scoped read grant. A remote result is accepted only if the provider/account, operation key, remote ID, and request fingerprint match the original binding. A mismatch, absent resource, multiple matches, stale read, incomplete response, wrong account, or unsupported provider result is `unknown` or `conflict`, never evidence that an effect did not happen.

Allowed outcomes are:

| Result | Durable behavior |
|---|---|
| Exact matching in-progress state | Append the observation, preserve the original case/hold and liabilities, schedule the next bounded read or owner review under the approved policy. |
| Exact matching terminal success | Append the exact remote state and response digest. Retain the original operation and all liabilities. The read worker does not mark business completion or clear a hold. Any business projection requires the existing stage-specific typed command and current authorization. |
| Authoritative no-effect result | Classify as no effect only when the provider contract proves an exact, sufficiently consistent lookup by the original idempotency key and its documented visibility window has elapsed. Append the proof. A subsequent action still requires the existing typed case command, fresh stage authorization, and a current permit; any permitted execution retains the original operation ID and request fingerprint. |
| Unknown, inconsistent, unavailable, or conflicting result | Keep the same work item and source case/hold open, append safe evidence, preserve liabilities, and alert/escalate. Do not submit, cancel, fabricate absence, or allocate a replacement operation ID. |

If a provider cannot prove exact lookup and a bounded authoritative absence window, production reconciliation for that provider remains HELD. A GET returning not-found is not by itself proof of no effect.

The read worker never changes a recovery case state. Case state changes use the existing revision-checked, idempotent, signed case command and its current authority checks. For an exact terminal success, retain the observation and keep the case reconciling until the existing stage-specific owner/projection records a terminal disposition; only then may the existing case terminalization command run. For authoritative no-effect, the recovery worker does not retry. A retry is allowed only through an existing typed path confirmed by the R33 owner, bound to the same operation and fingerprint, with current stage authorization and a fresh permit. If that path does not exist, remain held and leave the missing R33 contract explicit. A cycle may only be resumed through its existing typed command and stage-specific reauthorization. A closed-cycle publication hold stays immutable even after a matching remote read; any hold retirement or post-close business projection requires a separate reviewed design.

| Current source/result | Permitted case/hold behavior |
|---|---|
| Open-cycle reconciliation case, remote state still unknown | Keep the same case in `reconciling`; append observation and alert events. At a due production case deadline, the production deadline controller issues only the existing typed, separately authorized suspension/escalation transition for that same case revision and records its deduplicated wake in `v4_production_recovery_events`; it never invokes the fixture wait contract. |
| Open-cycle reconciliation case, exact terminal success | The worker appends evidence only. The existing stage owner/projector must record the terminal business disposition for the same operation; after the cycle is closed, the current `terminalize_case` command may move the case to `terminal`. |
| Open-cycle reconciliation case, authoritative no-effect | The worker appends proof only. A retry is prohibited unless the R33 owner supplies an existing typed, revision-checked command path that proves the no-effect observation, uses the same operation/request fingerprint, rechecks current policy/stop, and obtains a fresh stage permit. If that path is absent, retain `reconciling`/`suspended` and keep the liability held. |
| Closed-cycle production publication hold, any read result | Keep the work row fixed at `held`; append evidence and alert events. No case is opened and no existing case, cycle, hold, operation, or liability changes. |

The accepted state transitions remain those in the existing case trigger: review approval/rejection, bounded retry resume, deadline suspension, and terminalization after a committed terminal disposition. This increment adds no transition to `v4_recovery_cases` and does not interpret alert acknowledgment as a case transition.

## Alert, acknowledgment, and escalation contract

Create one alert-intent event in the same transaction as the recovery work row, and a distinct intent at each approved escalation level. Use the primary recovery owner and a preconfigured, target-approved on-call roster. Record the versioned recipient-profile identity and digest; do not accept caller-supplied email addresses, channels, or fallback recipients. The alert contains only the work/case/hold ID, original operation ID or safe digest, typed reason/state, deadline, target alias, and a stable inspection route that requires normal authentication. It excludes request bodies, user content, secret values, bearer tokens, signed URLs, and unbounded provider responses.

The channel must support a stable idempotency key or a read-only lookup by that key. After a timeout or process death following external acceptance, first query the same key or repeat the same request with that key. Never mint a new alert key to bypass uncertain delivery. If the provider can neither deduplicate nor confirm acceptance, record delivery as uncertain/held and escalate through the separately approved backup path; do not claim delivery.

An acknowledgment is a separate append-only event. It requires an authenticated human mapped to an enabled identity in the same workspace, current acknowledgment authority, the exact alert/work/source binding, and a provider message reference or authenticated application acknowledgment. It is idempotent by the stable alert ID. It means only “received”; it does not approve, resume, resolve, or alter the case, hold, operation, permit, or liabilities. The fixture database acceptance row never satisfies this requirement.

Delivery retry count, retry intervals, claim lease, owner response window, and escalation times must come from a named, versioned target operations policy approved by the alert/on-call owner. No code default or fixture retry count is a production policy. Transient network, throttling, or service errors retry only within that bound using the same alert key. Authentication failure, invalid recipient, payload rejection, expired owner, or exhausted retries moves the alert to visible held state and advances to the preconfigured on-call tier. If no tier is configured or all tiers are unavailable, retain the held work and evidence; the acceptance result is HELD. Alert outage never causes the recovery worker to drop the alert or retry the business effect.

An unacknowledged owner alert remains open until its policy response window. For case sources, the canonical `v4_recovery_cases` revision and deadline remain authoritative; the production worker reads them directly and records each due escalation as a separately deduplicated external alert. It does not dispatch `v4_runtime_waits` through the fixture driver. Hold alerts use the explicit target-specific recovery deadline. Missing or expired owners do not cause silent reassignment: record the owner failure and notify only the approved backup/on-call group. No acknowledgment automatically suppresses a required escalation while the recovery case or immutable hold remains unresolved.

## Stop, revocation, and restart behavior

At startup and before each read, claim, delivery, retry, acknowledgment, or escalation, read back the exact work, case/hold source, current stop revision, policy/revocation revision, route lease, and artifact compatibility. A stop/revocation race prevents any new provider read or business action. Alert delivery and acknowledgment continue only under their independent, currently valid communication scopes. Preserve the original source and existing alert intents. Any in-flight provider response after the fence is recorded as evidence only and cannot advance the business operation.

On recovery-worker restart, read the same durable work ID and original operation ID, validate the exact route and artifact floor, replay event identity, and reconcile any unexpired/expired alert claim before a new attempt. Lost acknowledgments repeat only the same read or the same external alert idempotency key. No restart creates a new recovery case, operation, provider request key, hold, or escalation tier for the same source and revision.

Rollback stops new recovery dispatch and waits for the supported worker route to drain. It retains all work rows, event history, cases, holds, alert intents, receipts, acknowledgments, and liabilities. A read-only reconciliation path may remain only if the policy owner explicitly authorizes it, the worker route is compatible, and the same current scope remains valid. Otherwise all recovery remains stopped and held.

Before restarting any prior application code, the routing-owned authenticated rollback-launcher ABI v2 runs the recovery-owned read-only `verify_p1_recovery_rollback_v2` against the exact target database before importing or executing that code. It discovers the complete affected workspace/source/work inventory itself; a caller-supplied list of operation or hold IDs cannot narrow the query. It reads the fixture hold relation, production immutable-hold work rows, their source cases/intents, every referenced production permit/claim/current pointer, and each liability snapshot version. It executes and records both reason predicates (`expired_permit_receipt` and `published_during_cancel`) on every run, even when either result count is zero. For each reason, zero, one, or many rows are valid inventory sizes only when the complete source query is used; every returned row is validated individually. The verifier rejects duplicate source identities, omitted rows, wrong reason/state pair, missing/NULL snapshot evidence, unsupported snapshot version, changed workspace/operation/reason, any changed liability, unknown route/action claim, incomplete query, or verifier outage. It deterministically hashes sorted source IDs, source and reason discriminants, snapshot versions and hashes, full liability fingerprints, permit/claim/pointer references, and the exact migration head into one inventory digest. The launcher records the read-only pre-exec digest and performs the same complete read after the prior artifact has restarted; IDs, counts, versions, and fingerprints must match. A partial, changed, or stale inventory denies before process execution/registration. The prior artifact, worker history, image, lock, interpreter, and migration head must meet the exact qualified production compatibility floor; 0043 alone is not enough. Do not downgrade migrations or remove production recovery evidence.

## Red-first acceptance tests

These behavioral tests start against the exact candidate and named environment. Fixture tests remain separately labeled and cannot pass a production row.

1. **Exact source and stable work identity:** concurrent adoption of the same cycle case, hold, or operationless `pre_admission_intent_case` returns one stable work ID; changed workspace, owner, source revision, operation, case revision, hold reason, target, or fingerprint conflicts. A closed-cycle `published_during_cancel` hold is linked without creating a case or reopening the cycle. An open-cycle `expired_permit_receipt` hold is retained without closing the cycle. The intent source requires NULL cycle/context/operation/remote target, and a successful wake preserves the same intent until current admission creates the cycle.
2. **Original operation read scope:** every provider request uses the original operation UUID, idempotency key, account, remote identity, request fingerprint, and a read-only grant for an eligible cycle case or hold. A `pre_admission_intent_case` is rejected before provider client construction and performs no provider read. Assert no submit, cancel, broad list, cross-account read, new operation, or changed request occurs on success, error, timeout, restart, or unknown state.
3. **Authority and stop races:** inject stop, grant revocation, policy outage, stale policy revision, and route-lease loss before claim, before GET, during GET, after response/before event commit, before alert send, and before acknowledgment. Each blocks unauthorized provider reads and all business actions, leaves the original case/hold and liabilities intact, and appends only evidence allowed under the recorded authority. A separate current communication scope may deliver or acknowledge an alert during an effects stop; no alert scope permits a provider effect.
4. **Result classification:** exact in-progress and terminal results bind to the original operation; a provider-specific authoritative no-effect result is accepted only after its documented lookup window. Not-found without that guarantee, wrong account, duplicate match, mismatched request/remote ID, partial response, stale response, or provider outage stays unknown/held and never triggers an effect.
5. **Crash and exact replay:** crash after a remote read but before evidence commit repeats only the same read; crash after event commit returns/reuses the committed observation identity. Crash after alert provider acceptance but before local receipt uses the same provider idempotency key or exact readback and yields one external message. Work and event identities do not fork.
6. **Production case-command and deadline controller:** with every fixture command/timer/notification route disabled, exercise current production-authorized review/resume, due-time suspension/escalation, terminalization, and R35 archive against the existing typed tables. Stale revisions, expired owners, changed policy, stop/revocation, route-fence loss, action exhaustion, and unknown liability reject commands. Concurrent due wake and process crash/replay yield one stable source/revision/action event and one case transition. The read worker cannot issue commands. For pre-admission intent, stale revision, stop/revocation, expiry, wake exhaustion, or restart records a hold and allocates no cycle; successful current admission preserves the intent ID and allocates a cycle only once. No new retry transition, case state machine, or archive ledger is introduced.
7. **Alert delivery and acknowledgment:** real authorized primary-channel delivery produces a provider receipt bound to one alert ID; duplicate dispatch yields one accepted message. Acknowledgment requires the mapped human and exact message/work binding, is deduplicated, and leaves the case/hold, operation status, and liability unchanged. A database fixture acceptance alone does not satisfy the external test.
8. **Owner and outage escalation:** primary owner unavailable, no mapped owner, channel authentication failure, throttling, network outage, lost acknowledgment, retry exhaustion, and unavailable backup group all retain visible work and immutable event history. Retry count and timing match the named versioned policy. No implicit recipient or provider substitution occurs.
9. **Two-reason concurrent hold insert and crash:** for `expired_permit_receipt` on an open cycle and `published_during_cancel` on a closed/cancelled cycle, test both the existing fixture path and the corresponding production immutable-hold path. Race concurrent exact insertions for the same original operation. Assert exactly one stable hold/work ID and unchanged complete liability snapshot. Then crash a real process immediately after the hold transaction commits but before typed failure/reporting; restart and replay the same operation, assert the same ID, exactly one hold row, and byte-equivalent complete before/after liability snapshots. Reject the wrong reason/state pair without changing liabilities. Altered operation, evidence, or reason conflicts.
10. **Complete rollback inventory before prior-code restart:** run the actual `verify_p1_recovery_rollback_v2` through the authenticated launcher ABI v2 before process execution. Verify that both reason predicates are executed against complete fixture and production sources; cover zero, one, and many rows for each reason independently, and mixed source inventories. Missing a reason row from a supplied partial list, omitting an extra hold, unsupported snapshot version, absent/NULL snapshot, changed workspace/operation/reason, changed liability, stale evidence, verifier timeout, 0043-only/below-production-floor artifact, or unknown route/action claim denies before execution/registration. For valid cases, compare complete sorted inventory IDs, counts, snapshot versions, fingerprints, and digest before and after restart. Zero rows for one reason pass only when the independent complete query proves none exist; both reason checks must still appear in the verifier result.
11. **Operationless intent restart and concurrency:** race two authorized workers adopting and waking the same `pre_admission_intent_case`; crash before wake commit and after wake/admission commit; restart with the same intent/revision; revoke authority or advance eligibility during the race; exhaust the configured wake limit; and attempt provider read/operation allocation before admission. Results are one stable intent work identity, correct stale/held disposition, no provider calls, and no cycle/context/operation until the successful canonical admission transaction.
12. **Schema and migration safety:** exact upgrade preserves all historical hold/case/notification rows. Source/event/command guards reject update/delete, cross-worksource binding, duplicate idempotency keys, malformed digests, unsupported reason/state pairs, operationless source with non-null operation/target, and unauthorized row insertion. Downgrade refuses populated production work/events/commands and leaves every source liability intact. No fixture row is automatically adopted as production.
13. **Exact candidate/environment evidence:** retain named owner and operator, exact application commit, source/image/artifact/lock digests, production migration floor, route/slot/epoch readback, provider/account and channel aliases, policy/recipient-profile revisions, operation/case/intent/hold IDs, remote response digests, external message/ack references, commands, UTC timestamps, reports, independent review, and SHA-256 of each evidence artifact. Fixture, CI, production, formal approval, and historical-candidate evidence remain distinct. Missing production target on the audited host yields NOT RUN/HELD.

## Observability and evidence

Expose bounded metrics by environment, route, and target: open recovery work by source/reason/owner and age; oldest unknown result; remote-read attempt count, result class, latency, stale or mismatched response count; current policy/stop revision; event-ledger replay/conflict count; pending/claimed/held alert count and age; delivery attempt count and provider latency; deduplicated delivery count; acknowledgment age; escalation level; owner/recipient availability; and rollback-verifier result. Structured logs include safe work, source, operation, route, slot, epoch, policy revision, alert ID, and short digests only. Never log credentials, raw requests, private provider data, or alert tokens.

Each evidence record is bound to the exact candidate commit, tree/artifact/lock digests, migration revision, named deployment and environment-manifest digest, route and provider/account identity, current policy and recipient profile revisions, owner/operator, and evidence timestamp. Include both pre- and post-readback for remote operations, exact hold snapshots, complete liability fingerprints, alert-provider receipts, acknowledgment identity, retries/escalations, and independent review. Any changed candidate, target, route, provider account, owner roster, alert channel, policy revision, stale observation, or environment digest invalidates the affected evidence and returns it to NOT RUN/HELD.

## Completion boundary

This design supplies only the production recovery, least-scope remote-read, external alert, acknowledgment, and escalation contract for R18, R32, R33, and R34, with the stated supporting interfaces. It does not qualify the current development host for production, enable production effects, close RG0/RG1, authorize P2, or permit a merge to `main`. The final exact-candidate/environment audit remains mandatory after implementation and external qualification; any FAIL, NOT RUN, HELD, stale evidence, missing owner, or environment mismatch keeps P2 blocked.
